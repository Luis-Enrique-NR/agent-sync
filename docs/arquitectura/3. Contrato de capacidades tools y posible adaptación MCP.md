# Contrato de capacidades, tools y posible adaptación MCP

- **Estado:** Propuesta
- **Fecha:** 2026-08-08
- **Rama:** `backend/ai`
- **Nota:** MCP se registra como idea, no como decisión tecnológica aprobada

## Contexto

Un usuario puede querer que su agente consulte inventario, calendario, CRM o búsquedas web, y que ciertas acciones generen correos o reuniones. El primer corte solo inyecta hechos mock al contexto. Para evolucionar, hay que separar lo que el agente está autorizado a hacer de la tecnología concreta que expone cada herramienta.

No se ofrecerá un permiso global de “todas las capacidades”. Cada capacidad debe concederse explícitamente, con alcance mínimo, límites y política de aprobación.

## Capacidad, tool y notificación

- **Capacidad:** permiso funcional configurado por el usuario, como buscar en internet o consultar disponibilidad.
- **Tool:** operación ejecutable que implementa una capacidad.
- **Acción con efecto:** tool que modifica estado externo, como reservar un horario o enviar un correo.
- **Notificación de plataforma:** consecuencia determinística de un evento, no una decisión libre del LLM.

Una alerta por `APPROVAL_REQUIRED` debe producirse aunque el modelo no solicite “enviar correo”. El AI Brain emite el evento y el servicio de notificaciones decide si entregarlo por UI, correo u otro canal.

Enviar un correo comercial a una contraparte sí sería una acción externa y debe pasar por la política de tools.

## Contratos propuestos

```text
ToolDefinition
- tool_id
- version
- description
- input_schema
- output_schema
- effect: READ | WRITE
- data_classification
- idempotency_supported

ToolGrant
- agent_id
- tool_id
- allowed_operations
- allowed_data_scopes
- approval_policy: AUTO | USER_RULE | ALWAYS
- rate_limit
- expires_at

ToolCall
- call_id
- tool_id
- tool_version
- arguments
- reason
- session_id
- proposal_revision

ToolResult
- call_id
- status
- structured_output
- provenance
- observed_at
- expires_at
- side_effect_reference
```

El proveedor LLM puede proponer un `ToolCall`, pero una capa determinística debe validar el grant, el schema, el scope y la política antes de ejecutarlo.

## Puerto del AI Brain

El dominio debería depender de una interfaz propia, por ejemplo `ToolGateway`, y no de un SDK específico:

```text
list_authorized_tools(agent_id) -> ToolDefinition[]
execute(call, grant_context) -> ToolResult
```

Esto permite usar mocks, APIs directas o adaptadores MCP sin cambiar las políticas ni los contratos de negociación.

## MCP como posible adaptador

Una opción futura es exponer búsqueda, CRM, calendarios o inventario mediante servidores MCP. Bajo esta idea:

```text
AI Brain
   ↓ ToolGateway propio
MCP Adapter
   ↓
Servidor MCP autorizado
   ↓
Fuente externa
```

MCP no debe conectarse directamente al modelo saltándose el gateway. La aplicación debe seguir controlando:

- Allowlist de servidores y tools.
- Identidad del usuario y scopes concedidos.
- Validación de schemas y tamaño de resultados.
- Timeouts, cuotas y reintentos.
- Auditoría e idempotencia.
- Clasificación de datos devueltos.
- Aprobación de efectos externos.

Quedan abiertas la selección de servidores MCP, el modelo de autenticación y la operación de credenciales. Por eso MCP permanece como alternativa evaluable y no como dependencia del siguiente corte.

## Política mínima por tipo de tool

| Tipo | Ejemplo | Política inicial |
|---|---|---|
| Lectura pública | Búsqueda web | Puede ser automática con cuotas y fuentes registradas. |
| Lectura privada | Consultar CRM o calendario | Requiere grant y scope del propietario. |
| Escritura reversible | Crear borrador de correo | Puede permitirse sin envío. |
| Escritura externa | Enviar correo o crear reunión | Regla del usuario o aprobación obligatoria. |
| Compromiso de recurso | Reservar stock u horario | Revalidación, idempotencia y operación transaccional. |
| Datos personales | Resolver teléfono o ubicación | Aprobación obligatoria y canal autorizado. |

## Búsqueda web y contenido no confiable

Los resultados de internet son datos no confiables, no instrucciones. Antes de incorporarlos al contexto se debe:

- Conservar URL, fuente, fecha y consulta original.
- Limitar longitud y tipos de contenido.
- Separar resultados de las instrucciones del sistema.
- Detectar o neutralizar intentos de prompt injection.
- Evitar que una página conceda permisos o modifique límites del agente.
- Exigir evidencia cuando un turno dependa de información externa cambiante.

## Flujo de ejecución propuesto

```text
LLM propone ToolCall
        ↓
Validación de schema y ToolGrant
        ↓
¿Tiene efecto externo sensible?
        ├── Sí → APPROVAL_REQUIRED
        └── No → ejecutar
                    ↓
              ToolResult sanitizado
                    ↓
              reanudar generación
```

Los guardrails vuelven a ejecutarse sobre cualquier candidato generado después de usar una tool.

## Estrategia incremental

1. Mantener inventario, calendario y búsqueda como ejecutores mock determinísticos.
2. Introducir `ToolGateway` y probar grants, fallos, timeout y resultados maliciosos.
3. Conectar una sola tool real de lectura.
4. Evaluar un adaptador MCP cuando los contratos internos estén estables.
5. Incorporar acciones de escritura únicamente con auditoría e idempotencia.

## Consecuencias y trabajo pendiente

- LangChain o MCP pueden facilitar adaptadores, pero no deben contener la política de seguridad autoritativa.
- Las credenciales reales deberán residir fuera de prompts, transcripts y eventos públicos.
- Transporte/Integración implementará conectores y entrega de notificaciones; AI Backend define intención, validación y resultado estructurado.
- Falta decidir si una tool puede ser compartida por varios agentes del mismo usuario y cómo se revocan grants activos.
