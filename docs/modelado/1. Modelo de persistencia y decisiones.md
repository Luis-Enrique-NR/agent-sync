# Modelo de persistencia, diccionario de datos y decisiones de diseño

- **Estado:** Aceptada
- **Fecha:** 2026-08-08
- **Rama:** `codex/ai-backend`

---

## 1. Contexto

El PRD y SRD definen entidades conceptuales (`AgentProfile`, `MatchSession`) y flujos de estado (`SEARCHING` → `ACTIVE` → `PENDING_HUMAN_APPROVAL` → `RESOLVED`/`REJECTED`) pero no especifican tecnología de persistencia ni esquema físico. El AI Brain (`/backend/ai`) opera sobre modelos Pydantic en memoria y necesita una capa de persistencia que los serialice sin acoplarse a su lógica interna. Las HU exigen trazabilidad notarial de decisiones (PRD §8), transparencia de conversaciones, y un vault separado para datos personales.

## 5. Diccionario de Datos

### 5.1 `agent_profiles`

|---------|------|-------------|-------------|
| `agent_id` | UUID | PK, default `uuid4` | Identificador único del agente |

| `entity_type` | VARCHAR(20) | INDEX, CHECK `IN ('company','person')` | Discriminador B2B/P2P |
| `status` | VARCHAR(20) | INDEX, CHECK `IN ('AVAILABLE','BUSY','PAUSED')` | Estado operativo en el ecosistema |
| `public_description` | JSON (TEXT) | NOT NULL | Descripción visible para otros agentes |
| `interests` | JSON (TEXT[]) | DEFAULT `[]` | Etiquetas de lo que el agente busca (matchmaking) |
| `capabilities` | JSON (TEXT[]) | DEFAULT `[]` | Etiquetas de lo que el agente ofrece (matchmaking) |
| `raw_profile` | JSON | NOT NULL | `AgentProfile.model_dump(mode="json")` — fuente de verdad |
| `created_at` | TIMESTAMP UTC | NOT NULL, DEFAULT `utc_now` | Fecha de creación del perfil |

| Columna | Tipo | Constraints | Descripción |
|---------|------|-------------|-------------|

| `portal_channel_id` | VARCHAR(100) | NULLABLE, INDEX | Canal efímero en Portal (lo asigna Ing. 1) |

| `agent_2_id` | UUID | FK → `agent_profiles`, INDEX | Segundo participante |
| `initiator_id` | UUID | FK → `agent_profiles` | Agente que disparó el matchmaking |
| `current_speaker_id` | UUID | FK → `agent_profiles`, NULLABLE | Agente con el turno actual |
| `status` | VARCHAR(30) | INDEX, CHECK `IN (SessionStatus)` | Estado del FSM |
| `turn_count` | INTEGER | DEFAULT 0 | Turnos ejecutados |

| Categoría | Acciones | Significado |

## 7. Decisiones de Diseño

### 7.1 Stack: SQLite + SQLModel

SQLModel fue elegido sobre SQLAlchemy puro porque sus modelos son compatibles con Pydantic v2 — el mismo ecosistema que usa el AI Brain. SQLite fue elegido porque requiere cero servidores externos (crítico para una demo de hackathon de 36h). La migración a PostgreSQL es trivial: solo cambia la URL de conexión.

### 7.2 Arquitectura de doble representación: columnas relacionales + JSON

Cada entidad que proviene del AI Brain (`AgentProfile`, `NegotiationState`) se persiste en dos capas:

- **Columna JSON (`raw_profile`, `raw_state`):** fuente de verdad. Contiene el `model_dump(mode="json")` completo del modelo Pydantic. Se pasa intacto de vuelta al motor con `model_validate()`.
- **Columnas relacionales:** caché derivada para queries, índices, joins y dashboards. Se reconstruyen desde el JSON en cada `save_*`. **Nunca se actualizan independientemente.**

Esta decisión evita duplicar la lógica de validación Pydantic en SQL y permite que el motor evolucione sin migraciones de esquema relacional.

### 7.3 Nuevos campos en `AgentProfile`

- `interests: list[str]` — etiquetas de lo que el agente busca. Alimenta el matchmaking (SRD §4.2).
- `capabilities: list[str]` — etiquetas de lo que el agente ofrece.
- `status: AgentStatus` — `AVAILABLE`, `BUSY`, `PAUSED`. Cubre HU P1 "Pausar mi agente".

Estos campos **no rompen el motor**: no son leídos por `guardrails.py`, `escalation.py`, ni `graph.py`.

### 7.4 Separación PII: `private_resolutions`

Los datos personales se almacenan en tabla separada con referencias opacas (`value_ref`). El AI Brain nunca recibe valores reales. La resolución ocurre post-aprobación humana en Backend API. Cumple `docs/seguridad/1`.

### 7.5 Estrategia `user_id` sin tabla `users`

`user_id` existe como `UUID` indexado en `agent_profiles` y `audit_records` **sin FK física ni tabla `users`**. Para el MVP basta con UUIDs mockeados. La trazabilidad del PRD §8 se cumple. La tabla `users` con autenticación real se implementa post-MVP.

### 7.6 Siembra automática de datos privados

`init_db()` ejecuta `seed_private_resolutions()` que inserta los valores de `persistence/fixtures.py` en `private_resolutions` si no existen. Es idempotente. Elimina la doble fuente de verdad entre el diccionario hardcodeado y la tabla SQL.

### 7.7 Fixtures actualizados

`b2b.json` y `p2p.json` incluyen `interests`, `capabilities` y `status: "AVAILABLE"` con valores representativos del negocio.

| Fixture | Agente | interests | capabilities |
|---------|--------|-----------|-------------|
| B2B | EcoTextiles | `raw_materials`, `organic_textiles` | `supply_textiles`, `bulk_shipping` |
| B2B | Norte Diseño | `manufactured_goods`, `sustainable_textiles` | `brand_design`, `quality_assurance` |
