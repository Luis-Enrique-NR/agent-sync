# Exploración accionable y alcance geográfico

**Estado:** Propuesta

**Fecha:** 2026-08-09

**Rama:** `style-design`

**Alcance actual:** diseño y datos simulados del frontend. No modifica el matchmaking del backend.

## Contexto

Un match semántico no siempre representa una oportunidad utilizable. Dos agentes pueden perseguir objetivos complementarios y, aun así, no tener una ruta razonable de entrega, desplazamiento o encuentro. Mostrar esos perfiles en `Explorar` crea una expectativa falsa y obliga al usuario a descubrir una incompatibilidad que el sistema podía descartar antes.

La ubicación exacta tampoco debe convertirse en un requisito del directorio. En P2P, la dirección y la ubicación en tiempo real son datos sensibles que siempre pasan por aprobación humana. Para descubrir compatibilidad basta una zona pública aproximada y una declaración de alcance operativo.

## Decisión de producto

`Explorar` no se comporta como un directorio de todos los perfiles registrados. Representa la salida explicable del filtro de descubrimiento y solo muestra agentes accionables para el agente propietario.

Para llegar a la vista, una pareja debe cumplir como mínimo:

1. objetivos complementarios en una dirección válida de demanda y oferta;
2. límites duros compatibles;
3. al menos un área de interacción compartida;
4. disponibilidad operativa para iniciar o continuar una conversación;
5. ausencia de exclusiones temporales como cooldown o bloqueo.

La interfaz muestra:

- zona pública aproximada, nunca una dirección;
- alcance declarado, por ejemplo local, nacional o con entrega internacional;
- explicación breve de por qué la interacción es viable;
- capacidades que la contraparte puede aportar;
- conversación existente únicamente cuando pertenece al agente del usuario.

Los perfiles descartados no aparecen como resultados. La vista puede comunicar cuántos fueron filtrados y agrupar el motivo, sin revelar identidades ni información de perfiles inaccesibles.

## Contrato propuesto

La ubicación pública y el alcance deben ser datos distintos:

```text
PublicArea
  country_code: string
  region_code: string | null
  city_code: string | null
  label: string
  centroid: coordenada aproximada opcional
  precision: COUNTRY | REGION | CITY | ZONE

InteractionScope
  mode: LOCAL | REGIONAL | NATIONAL | INTERNATIONAL
  service_area_codes: list[string]
  max_distance_km: number | null
  supports_shipping: boolean
  supports_in_person: boolean

DiscoveryCandidate
  owner_agent_id: UUID
  candidate_agent_id: UUID
  owner_objective_id: UUID
  candidate_objective_id: UUID
  actionable: boolean
  score: number
  public_area: PublicArea
  viability_reasons: list[string]
  exclusion_reason: null | GOAL | PRICE | REACH | AVAILABILITY | COOLDOWN
```

El frontend debería consumir únicamente candidatos con `actionable = true`. Los descartes agregados pueden entregarse como contadores por `exclusion_reason`.

## Regla de privacidad

- `EXACT_ADDRESS` y `LIVE_LOCATION` no forman parte de `PublicArea`.
- Un centroide de mapa debe representar una ciudad o zona amplia, no la posición del usuario.
- Compartir un punto de encuentro concreto continúa siendo una decisión sensible.
- La precisión pública debe ser elegida por el usuario y validada por políticas antes de publicarse.
- El frontend no debe inferir ni geocodificar direcciones privadas.

## Estado temporal del frontend

La demo implementa el concepto con metadatos públicos en `frontend/data/discoveryMock.ts`. `frontend/components/EcosistemaList.tsx` evalúa objetivos complementarios y áreas compartidas para decidir qué perfiles aparecen. También incorpora un candidato simulado que coincide por objetivo, pero queda fuera por alcance, para demostrar el descarte previo.

Esta lógica es deliberadamente provisional. No debe convertirse en una segunda implementación permanente de matchmaking dentro del navegador.

## Criterios de aceptación

- Un candidato con objetivos compatibles, pero sin alcance compartido, no aparece en `Explorar` ni inicia una conversación.
- El mapa solo recibe una ubicación pública con precisión limitada.
- La dirección exacta y la ubicación en tiempo real nunca aparecen en payloads de descubrimiento.
- Cada tarjeta explica qué puede aportar la contraparte y por qué la interacción es viable.
- Una conversación enlazada siempre pertenece al agente autenticado y al candidato mostrado.
- El backend es la única fuente de verdad de elegibilidad cuando se complete la integración.
