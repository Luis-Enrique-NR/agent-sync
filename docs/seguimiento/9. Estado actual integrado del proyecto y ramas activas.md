## Contexto

El proyecto avanzó en ramas paralelas para Frontend, AI Backend, Persistencia y Transporte. Este informe reconstruye qué contiene cada rama, qué fue validado realmente y qué falta para obtener un flujo end-to-end. Los conteos de commits son relativos al corte de `origin/main`; una rama integrada puede incluir el trabajo de varias ramas anteriores.

La revisión fue de solo lectura sobre las ramas remotas, salvo la creación de worktrees temporales para ejecutar pruebas y builds. Esos worktrees y sus dependencias fueron eliminados después de la validación.

- Es la fuente actual de documentación compartida.
- Contiene la estructura inicial del Frontend mediante el merge `4aef5`.
- No contiene las iteraciones actuales de `origin/frontend`.
- No contiene `/backend` ni los avances de AI, Persistencia, Transporte o EDA.

Publicar este informe agrega un commit documental posterior al corte. Por ello, las ramas de integración deberán actualizarse nuevamente desde `main` antes de fusionarse.

### `origin/frontend` — `b2477`

Comparación al corte: 7 commits propios y 2 commits de `main` pendientes de incorporar.

Incluye:

- Dashboard y control de pausa.
- Lista del ecosistema.
- Conversación agente-agente.
- Bandeja de decisiones sensibles.

- Store compartido entre pantallas con persistencia en `localStorage`.

Validación realizada:

npm run build   → compilación Next.js y TypeScript exitosa

Se generaron correctamente las rutas `/`, `/bandeja`, `/chat/[id]`, `/ecosistema`, `/historial` y `/setup`. La rama no define scripts de lint o pruebas automatizadas. Toda la integración sigue usando `mockData.json`; no existen llamadas `fetch` al Backend API ni suscripciones a eventos reales.

### `origin/backend/ai` — `5dc00`

El remoto contiene:

Consecuencia: otras ramas solo pueden integrar el contrato remoto anterior hasta que este avance sea convertido en commit y enviado a `origin/backend/ai`.

### `origin/feat/data-model` — `af398`

Comparación al corte: 2 commits propios —incluido el AI base— y 3 commits de `main` pendientes.

Incluye:

- Tablas `agent_profiles`, `negotiation_states`, `negotiation_outcomes`, `private_resolutions` y `audit_records`.
- Repositorio CRUD tipado.
- SQLite + SQLModel y fixtures de PII.
- Campos `interests`, `capabilities` y `AgentStatus` incorporados al dominio AI.

Brechas encontradas:

- No existen archivos `test_persistence*` ni pruebas de repositorio.
- El documento declara `real_value` en texto plano para el MVP; no debe usarse con PII real sin cifrado y gestión de llaves.
- Su metadata todavía referencia `codex/ai-backend` y debe actualizarse.
- Sus cambios en `models.py`, fixtures, `pyproject.toml` y README deberán reconciliarse con el avance local más reciente de AI.

Esta rama ya está incorporada en `feat/eda-worker`; no necesita integración separada si se usa ese tip.

### Cadena de Transporte — `2d29d` a `cd496`

Las ramas son incrementales y representan una sola línea de entrega:

1. Planificación y especificaciones OpenSpec.
2. Admisión de webhooks con HMAC-SHA256, comparación constante y ventana temporal.
3. Bus durable con Redis Streams.
4. Cliente Portal tipado.
5. Handoff operativo.
6. Corrección de administración de accesos Portal.

La documentación de Transporte confirma que todavía faltan acciones operativas externas:

- Desplegar `webhooks.url` en Portal.
- Obtener y custodiar el secreto de webhook.
- Asignar Redis real, persistencia, backups y alertas.
- Activar consumidores únicamente después de componer secretos y bus reales.

Estas ramas ya son ancestras de `feat/eda-worker`. Deben archivarse después de integrar el tip consolidado, no fusionarse individualmente.

|---|---|

| `main` + `frontend` | No |

Que Git pueda fusionar los archivos no demuestra compatibilidad funcional. Todavía hay que alinear:

- Los tipos del Frontend con `EngineEvent`, `DecisionRequest` y estados reales.
- `models.py` de Persistencia con los contratos nuevos de privacidad del AI Brain.

- Las reglas de publicación: solo `TURN_READY` con audiencia pública puede llegar a la contraparte.

```text

```text

Antes de integrar EDA se recomienda renumerar los dos documentos de Transporte como `10` y `11`, actualizar sus referencias y hacerlo en la propia rama de integración antes de que formen parte de `main`.

## Orden recomendado de integración

1. Convertir los cambios locales de `backend/ai` en un commit validado y publicarlo.
2. Crear una rama de integración desde `feat/eda-worker` e incorporar el nuevo commit AI.
3. Reconciliar `AgentProfile`, privacidad, eventos, dependencias, fixtures y README entre AI y Persistencia.
4. Incluir `eda*` en el paquete, completar el handler y agregar pruebas de Persistencia/EDA.
5. Actualizar la rama desde el `main` que contiene este informe y renumerar los documentos de Transporte.
6. Ejecutar toda la suite con un Redis desechable disponible; no aceptar skips en la validación final.
7. Fusionar `frontend`, sustituir gradualmente el store mock por API/eventos y conservar un modo demo reproducible.
8. Ejecutar un smoke test end-to-end y después archivar las ramas intermedias ya contenidas en el tip integrado.

## Criterio de “proyecto integrado”

El proyecto podrá considerarse integrado cuando una prueba reproducible demuestre:

```text
Frontend configura o carga agente
        ↓
Backend persiste perfil y publica presencia
        ↓
Portal/webhook ingresa evento autenticado
        ↓
Bus entrega evento una sola vez lógicamente
        ↓
EDA carga sesión y ejecuta AI Brain
        ↓
Estado y auditoría se persisten
        ↓
TURN_READY aparece en conversación
        ↓
APPROVAL_REQUIRED aparece en bandeja
        ↓
Usuario decide y Backend reanuda sesión
        ↓
Match/rechazo se refleja en historial
```

Hoy cada bloque tiene una base parcial, pero la cadena completa aún no está conectada.
