# Estado inicial del Frontend

- **Estado:** Completada
- **Fecha:** 2026-08-07
- **Rama:** `frontend`
- **Dominio:** Frontend UI (`/frontend`)

## Punto de partida

La rama se creó desde un `main` limpio sin código de frontend. El PRD asigna al Frontend el Core Loop (6 pantallas completas + 3 simplificadas) sobre React/Next.js, y el SRD delimita el dominio en `/frontend` con responsabilidad de configuración del agente, visualización de chats en vivo y bandeja de decisiones sensibles.

## Avance registrado

- Proyecto Next.js 16 (App Router, TypeScript, Turbopack) inicializado en `/frontend`.
- Layout raíz con marca AgentSync, navegación y estilos base compartidos.
- Estructura base de rutas del Core Loop:
  - `/setup` — configuración del agente (personalidad, objetivos, límites duros y categorías sensibles).
  - `/ecosistema` — lista de agentes activos (B2B y P2P en la misma vista).
  - `/chat/[id]` — detalle de conversación agente-agente con panel de decisión sensible.
- `mockData.json` inicial con 2 sets de datos sobre el mismo schema agnóstico (`entidad + objetivos + personalidad + límites`):
  - **B2B:** Telar Textil S.A. ↔ OrganicCotton Supply negociando precio de tela orgánica.
  - **P2P:** Valentina (vendedora de auto) ↔ Carlos (comprador) coordinando prueba de manejo.
- Categorías de decisión sensible por defecto: obligatorias no desactivables (datos de contacto, dirección, ubicación) + editables (precio final, compromisos, encuentro físico).
- Tipos TypeScript compartidos (`lib/types.ts`) alineados al modelo del SRD (`AgentProfile`, `MatchSession`, estados, decisiones).
- Build de producción verificado sin errores.

## Consecuencias y riesgos

- El `mockData.json` es la fuente única de la demo: cualquier cambio en el contrato de datos del Backend API debe reflejarse aquí y en `lib/types.ts`.
- El frontend aún no consume una API real; el paso a datos en vivo (persistencia + Portal) requiere reemplazar las lecturas directas del JSON por llamadas al backend.
- El panel de decisión es client-side (cambia estado local): la aprobación/rechazo real debe enviarse al backend y emitirse a Portal una sola vez.
