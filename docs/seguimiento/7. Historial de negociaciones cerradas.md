# Historial de negociaciones cerradas (Iteración 5)

- **Estado:** Completada
- **Fecha:** 2026-08-08
- **Rama:** `frontend`
- **Dominio:** Frontend UI (`/frontend`)

## Contexto

El PRD (§5.2, §7) pide un historial simple de conversaciones pasadas (sin dashboards) y que un match termine en "revelar contacto", no en chat interno. Hasta la Iteración 4 el frontend solo mostraba negociaciones activas; las sesiones terminadas no tenían una vista propia. Esta iteración agrega el historial de negociaciones cerradas, con diferenciación visual entre **match confirmado** (contacto revelado) y **acuerdo rechazado** por el usuario.

## Avance registrado

- **`mockData.json`**: dos nuevas sesiones terminadas para poblar el historial.
  - `ses-b2b-003` (`RESOLVED`): match B2B con `revealed_contact` (email de contacto revelado al cierre).
  - `ses-p2p-002` (`REJECTED`): descartada por precio mínimo, sin contacto revelado.
- **`MatchHistory`** (cliente): núcleo de la iteración.
  - Lista sesiones con estado final (`RESOLVED` / `REJECTED`).
  - **Filtros con conteos**: Todas / Matches / Rechazadas.
  - Match confirmado → panel "Contacto revelado" con nombre del agente y contacto (`revealed_contact`), más enlace a la conversación.
  - Rechazada → nota de que el acuerdo se cerró sin publicar contacto.
- **Ruta nueva `/historial`** (`app/historial/page.tsx`): métricas simples (matches vs. rechazadas) + delegación a `MatchHistory`.
- **Nav**: nuevo ítem "Historial".

## Consecuencias y riesgos

- `revealed_contact` y los estados finales son datos de mock; al conectar la API real el historial debe derivarse de sesiones terminadas del backend.
- El historial es de solo lectura para el MVP; el filtrado y conteos son locales.

## Trabajo siguiente
