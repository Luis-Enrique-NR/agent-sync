# Manual de controles y casos del TUI

- **Estado:** Aceptada
- **Fecha:** 2026-08-07
- **Rama:** `backend/ai`
- **Componente:** `backend/ai/tui.py`

## Propósito

El TUI es un arnés de desarrollo para observar y probar el AI Brain sin depender de Frontend, Portal, matchmaking o base de datos. Ejecuta una sesión en memoria, muestra los eventos retornados por `NegotiationEngine` y permite resolver decisiones humanas desde la terminal.

No es una pantalla del producto. Al salir del proceso, la sesión desaparece porque todavía no está conectada a la persistencia administrada por el rol de Dominio, Persistencia y Orquestación.

## Inicio

Desde `/backend`:

```powershell
python -m ai.tui --scenario p2p --provider scripted
```

Parámetros principales:

| Parámetro | Valores | Comportamiento |
|---|---|---|
| `--scenario` | `b2b`, `p2p` | Selecciona perfiles, límites, reglas y mock data. |
| `--provider` | `scripted`, `openai` | Usa turnos determinísticos o el LLM real. |
| `--model` | ID de modelo | Sobrescribe `AGENTSYNC_LLM_MODEL` para esta ejecución. |
| `--max-turns` | Entero positivo | Detiene el loop cuando alcanza el máximo. |
| `--timeout-seconds` | Entero positivo | Define el deadline total de la sesión. |
| `--auto-approve` | Bandera | Resuelve automáticamente decisiones para smoke tests. |

`scripted` no necesita credenciales y siempre sigue el mismo guion. `openai` necesita `OPENAI_API_KEY` en `backend/.env` o en el entorno y puede tener latencia, costo y variación entre ejecuciones.

## Cuándo aparecen los controles

Los controles solamente aparecen cuando el motor retorna:

```text
PENDING_HUMAN_APPROVAL
```

Esto puede ocurrir por dos clases de pausa:

1. Existe un candidato permitido, pero sensible: precio final, acuerdo, fecha o dato personal.
2. No existe candidato para aprobar porque el sistema alcanzó timeout o máximo de turnos.

Cuando existe candidato se muestran `A`, `R`, `E` y `Q`. Cuando no existe candidato, `A` se oculta porque no hay mensaje que pueda publicarse.

## Controles A, R, E y Q

### A — Aprobar

Disponible únicamente cuando existe `pending.candidate_turn`.

Flujo:

```text
Candidato sensible sin publicar
        ↓ A
DecisionRequest = APPROVED
        ↓
El candidato entra al transcript una sola vez
        ↓
Se emite TURN_READY
        ↓
El grafo continúa o termina la sesión
```

Si el candidato tiene intención `ACCEPT`, la sesión termina en `RESOLVED`. Si contiene `OFFER`, `COUNTER_OFFER` o `QUESTION`, se cambia el agente que debe hablar y la negociación continúa.

Aprobar un candidato sensible no permite romper límites duros. El candidato ya pasó por los guardrails antes de que apareciera la opción `A`.

### R — Rechazar

Descarta el candidato pendiente y termina la sesión actual:

```text
DecisionRequest = REJECTED
SessionStatus = REJECTED
```

El candidato no entra al transcript y no se emite `TURN_READY`. En la implementación mínima, rechazar significa finalizar la negociación; todavía no existe una opción separada de “rechazar esta propuesta y pedir otra”.

### E — Reemplazar

Permite que la persona escriba manualmente el turno que se enviará en lugar del candidato del agente. El TUI solicita:

1. Mensaje público.
2. Intención.
3. Términos numéricos opcionales.

Estos campos no son tres decisiones diferentes. Son tres representaciones coordinadas del mismo turno:

| Campo | Quién lo consume | Ejemplo | Para qué existe |
|---|---|---|---|
| Mensaje público | La contraparte y la UI | `Aceptamos el lote por 900 USD.` | Es lo que se lee en la conversación. |
| Intención | El motor | `ACCEPT` | Determina si continúa, se resuelve o se rechaza la sesión. |
| Términos numéricos | Guardrails y reglas | `price_usd=900:USD` | Permite verificar el precio sin intentar adivinarlo desde texto libre. |

En una UI de producto estos campos no deberían presentarse como datos técnicos. Frontend podría mostrar un editor de mensaje, un selector como “aceptar/contraofertar” y un campo de precio; luego construiría el `AgentTurn` estructurado internamente.

Intenciones disponibles:

| Intención | Uso |
|---|---|
| `QUESTION` | Pedir información sin realizar una oferta. |
| `OFFER` | Presentar la primera propuesta. |
| `COUNTER_OFFER` | Responder con términos diferentes. |
| `ACCEPT` | Aceptar los términos y resolver la sesión. |
| `DECLINE` | Rechazar definitivamente y terminar la sesión. |

Los términos numéricos completos usan:

```text
key=value:unit
```

Ejemplo:

```text
price_usd=335:USD, quantity=2:units
```

Cuando se está editando un candidato existente, el TUI precarga los términos. En ese caso:

- Presionar `Enter` conserva los términos originales.
- Escribir solamente `880` cambia el único término existente y conserva `price_usd` y `USD`.
- Escribir `price_usd=880:USD` hace lo mismo de manera explícita.
- Si existen varios términos, se debe usar el formato completo para evitar ambigüedad.

Si el mensaje dice `Acepto 335 USD`, también debe existir `price_usd=335:USD`. Si no se declara, el guardrail lo bloquea como `UNSTRUCTURED_CURRENCY_AMOUNT`.

El reemplazo vuelve a pasar por límites duros y detectores de privacidad. No puede utilizarse para vender por debajo del mínimo, superar el presupuesto o escribir directamente teléfonos, emails, coordenadas o direcciones.

Como el reemplazo fue escrito durante una intervención humana explícita, no vuelve a crear la misma solicitud de escalamiento. Si pasa los guardrails, se publica y el grafo continúa según su intención.

## Ejemplo real de reemplazo B2B

El candidato pendiente es:

```text
Mensaje: Aceptamos el lote por 900 USD.
Intención: ACCEPT
Término: price_usd=900:USD
```

### Caso 1: cambiar únicamente la redacción

El usuario selecciona `E` y escribe:

```text
Nuevo mensaje: Aceptamos los 900 USD, sujeto a confirmar la fecha de entrega.
Intención: ACCEPT
Términos: Enter
```

Resultado: se conserva `price_usd=900:USD`, el mensaje pasa los guardrails, se publica y la sesión termina en `RESOLVED`.

### Caso 2: convertir la aceptación en contraoferta

```text
Nuevo mensaje: Podemos cerrar el lote por 880 USD.
Intención: COUNTER_OFFER
Términos: 880
```

El TUI transforma el valor simple en:

```text
price_usd=880:USD
```

Resultado: publica la contraoferta, cambia el turno a EcoTextiles y la negociación continúa. Para seguir una rama libre como esta se debe usar `--provider openai`; el proveedor `scripted` está diseñado para el guion fijo de smoke test y puede quedarse sin turnos al desviarse.

### Caso 3: hacer una pregunta sin aceptar

```text
Nuevo mensaje: ¿Los 900 USD incluyen la entrega?
Intención: QUESTION
Términos: Enter
```

El precio sigue declarado de forma estructurada porque aparece en el mensaje, pero la sesión no se resuelve: el turno pasa a EcoTextiles para responder. Igual que en el caso anterior, una conversación abierta requiere el proveedor real o un guion adicional.

### Por qué `900` fallaba anteriormente

La primera versión solo aceptaba el formato completo `key=value:unit`. Por eso escribir `900` producía:

```text
Formato inválido: usa el formato key=value:unit
```

El flujo fue ajustado: cuando hay exactamente un término pendiente, un valor simple reutiliza automáticamente su clave y unidad.

### Q — Salir

Finaliza el TUI sin resolver la decisión pendiente y retorna código de salida `130`.

No publica el candidato ni cambia el estado a `REJECTED`. Como el TUI actual no persiste sesiones, ese estado pendiente se pierde al cerrar el proceso. Cuando exista persistencia, `Q` deberá guardar la sesión como pendiente para continuarla posteriormente.

## Caso B2B guionado

Comando:

```powershell
python -m ai.tui --scenario b2b --provider scripted
```

Secuencia:

```text
EcoTextiles ofrece 900 USD
        ↓
Norte Diseño intenta aceptar 900 USD
        ↓
Regla FINAL_AGREEMENT
        ↓
PENDING_HUMAN_APPROVAL
```

- `A`: publica la aceptación y termina en `RESOLVED` con dos turnos.
- `R`: no publica la aceptación y termina en `REJECTED` con un turno.
- `E`: reemplaza la aceptación. `ACCEPT` resuelve; una pregunta u oferta continúa.
- `Q`: cierra la prueba dejando conceptualmente la decisión pendiente.

## Caso P2P guionado

Comando:

```powershell
python -m ai.tui --scenario p2p --provider scripted
```

Secuencia:

```text
Valentina ofrece 340 USD
        ↓
Mateo contraoferta 330 USD
        ↓
Valentina acepta 330 USD y propone compartir su PHONE
        ↓
MANDATORY_PERSONAL_DATA + regla del usuario
        ↓
PENDING_HUMAN_APPROVAL
```

- `A`: publica el mensaje autorizado y termina en `RESOLVED` con tres turnos.
- `R`: el mensaje con la propuesta de compartir contacto no se publica y termina en `REJECTED`.
- `E`: permite enviar otro mensaje seguro sin revelar el teléfono directamente.
- `Q`: sale sin publicar el candidato.

El teléfono real no está dentro del escenario ni se revela desde el TUI. Cuando Valentina genera su turno, su LLM puede recibir `contact_ref_valentina_phone` dentro de `speaker_private_context`, porque la referencia le pertenece. La solicitud de aprobación interna conserva esa referencia para auditoría y posterior resolución segura.

Después de aprobar, el transcript público y el evento `TURN_READY` conservan únicamente la categoría `PHONE`; no contienen `contact_ref_valentina_phone`. Cuando Mateo genera el turno siguiente tampoco recibe esa referencia en su prompt. Resolverla y entregar el valor real, después de contar con autorización, será responsabilidad de una capa segura externa al AI Brain.

## Diferencia entre pedir y proponer datos

Son operaciones distintas aunque el mensaje natural pueda sonar parecido:

| Operación | Contrato | Ejemplo | ¿Lleva `value_ref`? |
|---|---|---|---|
| Pedir un dato a la contraparte | `DataRequest` | Mateo pide un teléfono para coordinar. | No; solo categoría y propósito. |
| Proponer compartir un dato propio | `ProposedDisclosure` | Valentina propone compartir su teléfono. | Sí, pero únicamente en estado y eventos internos. |

Un agente nunca puede pedir un dato utilizando una referencia de la contraparte, ni copiar una referencia observada en un turno anterior. El guardrail valida que cada `ProposedDisclosure.value_ref` pertenezca al agente que está hablando.

Frontera de publicación:

```text
ProposedDisclosure del hablante
        ↓ guardrail + escalamiento
APPROVAL_REQUIRED [INTERNAL, conserva value_ref]
        ↓ aprobación humana
TranscriptMessage [sin value_ref, conserva categoría]
        ↓
TURN_READY [PUBLIC, sin value_ref]
        ↓
Prompt de la contraparte [sin value_ref]
```

## Timeout y máximo de turnos

Cuando se alcanza uno de estos límites, la pausa no contiene candidato:

```text
Motivo: TIMEOUT o NON_CONVERGENCE
Opciones: R, E, Q
```

- `R`: termina la sesión como rechazada.
- `E`: permite introducir un turno manual seguro. En la implementación actual debe usarse `ACCEPT` o `DECLINE` para cerrar una sesión que ya agotó su deadline.
- `Q`: cierra el proceso sin resolver la pausa.
- `A`: no aparece porque no existe un candidato generado que aprobar.

Actualmente el deadline se calcula desde el inicio de la sesión y también incluye el tiempo que una persona pasa leyendo o editando una decisión. Por eso un reemplazo no terminal como `QUESTION` o `COUNTER_OFFER` volverá inmediatamente a `TIMEOUT` si el deadline ya expiró. El comportamiento futuro recomendado es pausar el reloj mientras se espera al humano o conceder un nuevo presupuesto de ejecución al reanudar.

Para pruebas manuales con OpenAI conviene ampliar temporalmente el límite:

```powershell
python -m ai.tui --scenario p2p --provider openai --timeout-seconds 300
```

## Ejemplo: contraoferta seguida de timeout

Secuencia observada:

```text
Valentina genera una oferta de 360 USD con PHONE y MEETING_POINT
        ↓
El usuario selecciona E
        ↓
Mensaje: ¿Te parece bajarlo a 350 USD?
Intención: COUNTER_OFFER
Término: 350 → price_usd=350:USD
        ↓
Se publica la contraoferta y el turno pasa a Mateo
        ↓
El deadline vence antes de obtener el siguiente turno
        ↓
PENDING_HUMAN_APPROVAL por TIMEOUT, sin candidato
```

Para terminar esa sesión desde la segunda opción `E`:

```text
Nuevo mensaje: Sí, acepto comprarla por 350 USD.
Intención: ACCEPT
Términos: price_usd=350:USD
```

En esta segunda pausa no existe un candidato cuyos metadatos puedan reutilizarse, por eso se debe escribir el término completo. Mateo tiene un límite `price_usd lte 360 USD`, así que aceptar `350 USD` pasa el guardrail y termina en `RESOLVED`.

Alternativa para terminar sin acuerdo:

```text
Nuevo mensaje: No deseo continuar con la compra.
Intención: DECLINE
Términos: Enter
```

## Modo auto-approve

Ejemplo:

```powershell
python -m ai.tui --scenario p2p --provider scripted --auto-approve
```

Reglas actuales:

- Si existe candidato pendiente, el TUI selecciona `APPROVE`.
- Si la pausa es timeout o no convergencia y no existe candidato, selecciona `REJECT`.

Este modo se usa para smoke tests y CI. No representa la experiencia real del usuario.

## Mapa de responsabilidades

El TUI sí prueba:

- Generación o reproducción de turnos.
- Guardrails.
- Escalamiento.
- Pausa y reanudación.
- Estados y eventos retornados por el AI Brain.

El TUI no prueba:

- Persistencia después de cerrar el proceso.
- Envío real de eventos por Portal.
- Matchmaking.
- Autenticación.
- Resolución real de datos privados.
- Pantallas de Frontend.
